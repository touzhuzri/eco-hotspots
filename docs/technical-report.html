摘要

问题。天然产物数据规模大、字段多，结构、来源物种、化学分类与文献分散在数据库、论文和网页中。通用对话模型可以“讲知识”，却无法可靠回答“LOTUS 里菊科有多少条黄酮”，也容易把记忆中的数字当成事实。

方案。「世界之树」把 LOTUS frozen 260413（227,319 条结构）组织成一棵可交互的 WebGL 星点树，并在站内提供 AI 分析坞：模型不直接背数字，而是通过 11 个服务端工具查询 LOTUS、检索知识库、读取论文、分析表格、识图、驱动 3D 场景；复杂问题走“计划—执行—反思—简报”的研究流程；资料中的数量断言用确定性工具与 LOTUS 核对。

结果。Agent 任务级评测 18/18 通过，RAG 30 题 Hit@4 30/30、MRR 1.000、Cite@4 30/30，端到端测试 20/20，单元测试 15/15。系统为静态前端 + 零依赖 Node 服务，单端口部署，可在普通云主机或校园服务器运行。

关键词：天然产物；LOTUS；WebGL；AI Agent；工具调用；RAG；多模态；可核对溯源

01项目概述

1.1 背景与问题

LOTUS 是当前规模最大的开放天然产物结构数据库之一。本项目使用 frozen 260413 快照，包含 227,319 条结构记录、1,602 个物种节点和 2,038 个精选分子。对教学与科普来说，它既是宝贵的数据底座，也带来三个现实问题：

  • 看不见。表格与字段适合检索，不适合建立“某类分子在哪些科里出现”的直觉；传统 2D 列表也很难展示 20 万级结构的整体分布。
  • 查不动。要回答“哪个科的黄酮最多”，需要在分类、来源科、分子式、质量等多个字段间组合筛选，普通访客难以完成。
  • 信不过。通用大模型可以流畅地讲天然产物，却无法访问本地 LOTUS，容易把记忆中的数字当成事实；论文、网页与数据库口径不一致时，也缺少可核对的机制。

1.2 作品定位

「世界之树」不是把聊天框贴到网页上，而是把 数据查询、空间可视化、文献阅读与多模态识别 组织成一个可核对的分析工作台：

  • 空间层：每一颗星是一个天然产物结构；树冠、树干、根际与土壤对应来源生物的生态位置，支持缩放、检索、点亮、连线与领养。
  • 分析层：AI 分析坞直接调用服务端工具查询 LOTUS、聚合统计、画图、找相似分子、驱动 3D 场景；数字不经过模型记忆。
  • 证据层：RAG 回答标注《文件名》第 N 段、DOI 或 URL；资料中的数量断言用 verify_claim 与 LOTUS 做确定性比较，冲突时生成核对卡片。
  • 研究层：复杂问题按“计划—执行—反思—简报”推进，反思由服务端规则生成，不额外消耗模型额度。

03系统架构设计

3.1 总体架构

系统采用“静态前端 + 零依赖 Node 服务 + AI 分析代理”的形态。浏览器只访问一个公开端口；静态站负责文件分发、同源代理与安全路径屏蔽；领养服务与 AI 服务默认只绑定 127.0.0.1。这样既避免了跨域与多端口暴露，也让 Key、日志与账本留在服务端。

3.2 前端分层

层职责代表文件

前端不引入 React/Vue 等框架，也不使用打包器：原生 ES Modules 直接运行，减少构建与部署成本。稳定契约是 engineApi 与同源 /api，因此 UI 可以替换，数据与 AI 工具不必跟着改。

3.4 数据层

  • LOTUS 元数据：按 InChIKey 前两位分片压缩在 data/molecules/，按需加载；facets 与合法 InChIKey 集合单独存放。
  • 3D 构象：data/molecules3d/ 存放由 LOTUS SMILES 经 RDKit ETKDG 离线生成的构象，约 202,665 个；缺失时回退 2D 结构式。
  • 相似度索引：Morgan 指纹（r=2，1024 bit）+ Tanimoto，已在 data/similarity/ 生成，可由 pipeline 重建。
  • 知识库：data/kb-seed/ 是随仓库提交的种子（LOTUS 卡片、论文、权威网站）；运行时正文与向量在 data/kb/，不进入 Git。
  • 状态：claims.jsonl 是唯一必须长期保留的领养账本；.run/ 与 logs/ 可随时删除。

3.6 技术选型

技术选择理由替代方案与取舍

04AI 技术方案

4.1 设计目标与原则

AI 部分的目标不是“让模型多说话”，而是让它在天然产物数据上说得准、查得到、可核对、能部署。由此确定五条原则：

  1. 工具优先（tool-first）：数量、分类、来源科等事实必须由服务端工具返回；模型只负责理解问题、选择工具与组织解释。
  2. 证据契约：LOTUS、论文、网站、用户文档使用不同引用格式；冲突时以 LOTUS 为准并说明差异。
  3. 可降级：向量不可用退回 local-hash + BM25；视觉不可用退回文本；模型繁忙时重试并提示。
  4. 供应商无关：统一 OpenAI 兼容接口，模型与向量服务可独立替换。
  5. 秘密留在服务端：浏览器只发同源请求，不接触 Key、系统提示词或原始账本。

4.2 模型选型理由

角色选型理由
对话 / 工具调用DeepSeek V4 Pro（OpenAI 兼容）中文理解与函数调用稳定；长上下文适合多轮工具结果；成本适合公网演示；可一键切换 GLM / MiMo / 自定义。
视觉结构化DeepSeek Flash（可换 GLM-4V / 本地 Ollama）只需输出固定 JSON，不需要复杂推理；低延迟、低成本；与对话模型分开配置，避免互相牵制。
向量检索BAAI/bge-m3（1024 维）中英多语、语义检索质量高；SiliconFlow 免费档可用；与对话服务商解耦，换模型不影响 RAG。
Agent 框架自研轻量工具循环（不引入 LangChain / LlamaIndex）链路透明、可审计、零 npm 依赖；工具 schema、SSE 事件、限流与中止都可控；部署体积小。

不使用通用 Agent 框架的原因很实际：本项目的工具是强领域、强确定性的（LOTUS 查询、表格统计、DOI 检索），不需要复杂的多 Agent 编排；自研循环可以把“数字必须来自工具”“来源必须标注”等约束写进系统提示词与执行器，而不是依赖框架的默认行为。

4.3 集成方式

前端通过 fetch 读取 SSE，按事件类型增量渲染。模型请求统一为 POST /chat/completions（流式 + function calling）；服务端把工具结果作为 tool 消息追加回上下文，直到模型给出最终回答或达到轮次上限。配置读取顺序为：ai/.env → 运行时 .run/ai-config.json → 内置默认值；公开部署可开启 AI_CONFIG_LOCK，前端只能读 hasKey，不能读 Key。

4.5 Agent 循环与执行控制

  • 循环：理解问题 → 选择工具（可并行）→ 执行 → 把结果回填 → 继续或总结。默认最多 16 轮，可通过 AI_MAX_TOOL_ROUNDS 调整。
  • 约束：每轮限制 web_search 与 search_papers 的调用次数，避免反复换关键词消耗额度；工具失败时给出可执行下一步。
  • 重试：对 429 / 5xx / “访问量过大”做指数退避；个别服务商不识别 thinking 参数时自动去掉并记住，避免整轮失败。
  • 中止：用户点停止 → 浏览器 AbortController 断开 → 服务端监听 res.on("close") → 中止上游模型请求与工具执行，避免后台继续烧额度。
  • 可观测：/api/ai/metrics 记录对话数、模型调用耗时、工具成功率、视觉与文献检索次数，不记录问题正文与 Key。

4.6 RAG 检索与引用

  • 解析：支持 PDF、Word、Excel、PPT、CSV 与纯文本。PDF 处理间接 /Filter、Flate / ASCII85 / ASCIIHex / RunLength、对象流与 ToUnicode CMap；扫描版或加密 PDF 会返回明确原因。
  • 切块：默认每段 500 字、重叠 80 字，单文档最多 240 段；知识库最多 200 个文档（可配置）。
  • 检索：向量余弦与词法覆盖率融合，默认 AI_KB_MIN_SCORE=0.32；对话内自动召回使用略低阈值，避免漏掉长文档。
  • 引用：系统知识库与用户文档标注《文件名》第 N 段；论文标注第一作者、年份、期刊、DOI；网站标注站点名与 URL。
  • 评测：30 题覆盖 LOTUS 卡片、论文、权威网站与数据局限性；Hit@4、MRR、KW@4、Cite@4 全部可复现。

4.7 多模态：先结构化，再核验

视觉模型不直接给结论，而是被要求输出固定 JSON：图片类型、主体、科属候选（含置信度与理由）、分子候选（含置信度与结构特征）、可见文字、不确定项与总体置信度。服务端随后：

  1. 把结构化结果作为 vision 事件推给前端，先让用户看到“模型看到了什么”；
  2. 对达到置信度阈值的分子/科属候选自动调用 query_molecules，并对首个命中调用 find_similar；
  3. 根据命中结果生成分类分布图与场景定位；低置信度候选不自动查库；
  4. 把核验结果交回文本模型，要求明确写出不确定性与“仅凭图片无法确认”的边界。

这样把“识图”拆成“抽取候选”和“数据核验”两段：前者可能出错，后者必须落到 LOTUS；即使视觉模型判断错，用户也能从工具轨迹看出哪一步没有命中。

4.8 研究任务：计划—执行—反思—简报

  • 计划：模型先输出目标与 2–4 个步骤（含建议工具），作为后续执行的约束；允许根据工具结果调整。
  • 执行：每个工具轮次通过 SSE 推送 step / tool / chart / source，用户能看到“查了什么、拿到什么”。
  • 反思：服务端检查工具失败、空结果、来源缺失、图片低置信度等条件，生成局限与下一步；不额外调用模型。
  • 简报：导出包含问题、计划、结论、反思、工具记录、图表数据、来源、数据核对与分子记录的 Markdown；最近一次研究同时保存在浏览器与服务端匿名会话。

4.9 数据核对与可点击溯源

资料中经常出现“某科有 N 条”的断言，但论文口径、数据库版本与筛选条件可能不同。系统提供 verify_claim：模型从资料中抽取 claimed 数字与筛选条件，服务端查询 LOTUS 后由 ai/verify.mjs 做确定性比较，返回：

{ claimed, actual, delta, percent, tolerance_pct, verdict }
verdict = |percent| <= tolerance_pct ? "consistent" : "conflict"

当判定为冲突时，前端生成「数据核对」卡片，显示资料值、LOTUS 实际值、差异百分比与容差，并把结果写入研究简报。另一个细节是分子 chip：query_molecules、find_similar、explain 返回的分子会渲染为可点击标签，点击后收起对话、选中该分子并飞到 3D 场景，实现“回答 → 数据 → 空间”的闭环。

  • 小助手导览：每次进入询问是否带看；开始后用约 15 秒介绍世界树、左栏、右栏与 AI 研究台，讲完或点“跳过”都会打开 AI。
  • 穿梭群星：镜头贴近冠层星点再拉出，掠过树干与根际，最后回到全树；用相机路径与缓动营造“穿行”感。

5.3 AI 分析坞

AI 分析坞是前端最复杂的组件（约 2,100 行）。它维护消息、计划、工具轨迹、来源、图表、冲突卡片、会话与导出状态，并把 SSE 事件映射为可读的界面：

事件界面表现
status连接模型、重试、工具执行等等待提示
plan / step研究计划卡片与步骤进度
tool工具名、参数摘要、结果计数；失败时显示原因
source《文件名》第 N 段、DOI、URL 引用卡片
chart柱状 / treemap / 散点图
vision图片结构化卡片：主体、候选、置信度、不确定项
conflict资料值 vs LOTUS 实际值、差异百分比、容差

分子 chip 让回答中的分子可点击：点击后收起对话、选中分子、飞到详情卡；这让 AI 的文本结论与 3D 空间位置形成可验证的对应关系。

5.4 文件、表格与 PDF

  • 格式：PDF、Word（docx）、Excel（xlsx）、PPT（pptx）、CSV/TSV、纯文本；前端限制体积，服务端再次校验。
  • PDF：支持间接 /Filter、Flate / ASCII85 / ASCIIHex / RunLength、对象流与 ToUnicode CMap；对扫描版、加密、字体编码缺失分别返回可读原因，而不是笼统的“二进制文件”。
  • 表格：parseDelimited 支持逗号/制表符/分号、引号、重复列名；上限 50,000 行 × 60 列；analyze_table 做分组计数、求和、平均、最小/最大，返回 groups 并自动生成柱状图。
  • 边界：Excel 只读第一个工作表；统计不经过模型手算；表格内容只用于本轮上下文，不作为长期知识库。

5.5 分子详情、结构式与领养

  • 结构式：按需加载 RDKit.js 与 WASM，在浏览器内解析 SMILES 并渲染暗色 2D 结构；不阻塞首屏。
  • 3D 构象：优先加载 data/molecules3d/ 分片；缺失时回退 2D。3D 视口支持拖动旋转与滚轮缩放，点击视口外返回世界树。
  • 领养：一个 InChIKey 只能被领养一次；同一 visitor token 可领养多颗并改名；名字留空显示“神秘用户”；只保存 key、显示名、时间与 token 哈希，不保存 IP/UA/邮箱。
  • 分享：permalink 同步选中分子、筛选与相机状态；打开链接可恢复同一视角。

5.6 前端性能与可维护性

  • 按需加载：LOTUS 元数据与 3D 构象按 InChIKey 前缀分片，首屏只加载当前视野所需数据；RDKit 在首次打开结构式时加载。
  • 无 CDN：Three.js、RDKit、MediaPipe 均放在 vendor/，离线环境也能运行。
  • 无构建：源码即产物，减少打包配置与版本漂移；CSS 使用变量组织主题，便于统一调整。
  • 契约稳定：数据字段见 src/data/contract.js，用途字段允许 null；UI 不直接拼 LOTUS 过滤逻辑。

07创新点说明

7.1 技术创新点

#创新点具体做法与价值
1数据接地的工具型 Agent把 LOTUS 查询、相似度、表格统计、数量核对都做成服务端确定性工具；系统提示词强制“先工具后数字”。与普通聊天式问答相比，回答中的数量、分类与来源科可被工具轨迹逐条验证。
2确定性数据核对与冲突卡片verify_claim 把资料中的数量断言与 LOTUS 实际统计做差值/百分比比较，冲突时生成可视化卡片并写入简报。模型不参与计算，避免“看起来合理”的假一致。
3计划—执行—规则反思的研究流程复杂问题先出 2–4 步计划，再执行工具；反思由服务端规则检查（失败、空结果、缺来源、图片低置信度）生成，不额外调用模型，兼顾研究深度与成本。
4混合 RAG 与可降级引用bge-m3 语义向量 + BM25 中文二元组融合；向量服务不可用时自动回退 local-hash，回答不中断；引用契约统一到文件名/段落、DOI、URL。
5先结构化再核验的多模态视觉模型只输出带置信度的候选 JSON，服务端再自动查 LOTUS、找相似、画分布；低置信度不自动查库，不确定项强制进入回答与简报。
6零依赖单端口架构与可中止流静态站、领养、AI 均为 Node 内置模块实现；一个公开端口完成同源代理；客户端 abort 通过 res.on("close") 传播到上游模型，停止后不再消耗额度。

08总结与展望

8.1 总结

「世界之树」完成了从数据到界面、从模型到证据的完整闭环：

  • 数据层：LOTUS 227,319 条结构、3D 构象、相似度索引与两层知识库，均可独立重建。
  • 交互层：22 万级 WebGL 星点树、生态层位、节气环、季节花瓣、闲置钟表、导览与穿梭，兼顾性能与科普表达。
  • AI 层：11 个工具、工具循环、混合 RAG、多模态、研究任务、数据核对、会话恢复、限流与中止。
  • 证据层：数字走 LOTUS，文档给段落，论文给 DOI，网站给 URL；冲突时给出双方数值与差异。
  • 工程层：零依赖 Node、单端口部署、环境变量模板、离线包、公网防护与可复现测试。

实测结果说明系统不是“演示壳”：Agent 18/18、RAG 30/30、E2E 20/20、单元 15/15；这些数字与脚本都随仓库提供，评委可以自行复现。

8.2 不足

  • 评测规模：18 条 Agent 任务与 30 条 RAG 题只能作为回归基线，不能覆盖全部真实问题；关键词判断是字符串包含，不判断语义完全正确。
  • 延迟：首字与总耗时受服务商影响明显；本机测试中正文增量在流末尾集中到达，首字指标与总耗时接近。
  • 视觉识别：植物照片与结构式的识别仍依赖通用视觉模型；低质量图片、手绘结构式与罕见物种的准确率有限。
  • 数据边界：LOTUS 不提供药效、安全性或临床结论；本项目明确不做医学建议，相关问题的回答范围有限。
  • 多用户：当前只有匿名会话，没有账号体系；领养账本适合单机/小规模部署，尚未做分布式一致性。
  • 移动端：已做响应式抽屉，但 22 万点场景在低端手机上的帧率与发热仍需继续优化。

8.3 展望

  1. 更强的结构理解：接入 OSRA / DECIMER 等结构式识别模型，把图片中的化学结构直接转成 SMILES 再查 LOTUS，减少对通用视觉模型的依赖。
  2. 更完整的证据链：为每条 LOTUS 记录补充文献出处与实验数据链接；把论文中的化合物—活性—物种关系抽取成可查询图谱。
  3. 教学与协作：增加教师模式、课堂任务、注释与收藏共享；在匿名会话之上提供可选账号，支持跨设备研究项目。
  4. 评测与可观测：扩大 Agent 任务集与真实用户问题集；把工具成功率、延迟、引用准确率做成持续回归看板。
  5. 部署与性能：提供容器镜像与一键脚本；对移动端做点云 LOD、分帧加载与 GPU 预算控制。
结语：天然产物数据已经足够大，下一步不是再做一个列表，而是让数据“可看见、可提问、可核对”。世界之树是一次面向教学与科普的尝试：让 AI 的每一句话，都能回到一颗具体的星。
